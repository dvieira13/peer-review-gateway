### V1. No authentication: any caller can act as any user

| | |
|---|---|
| **CWE** | CWE-306 Missing Authentication for Critical Function (related: CWE-862, CWE-290) |
| **OWASP (course list)** | A01 Broken Access Control; A07 Identification and Authentication Failures |
| **CVSS v3.1** | `CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:N` = **9.1 Critical** |
| **Layers** | API routing, application logic, identity data |

- **Root cause:** the application has no concept of an authenticated caller. `app.ts` registers the routers with no authentication middleware. The caller's identity is whatever `reviewer_id` and `reviewer_role` say in the request body (project decision 5), checked only against a static list of mock users whose ids (`fac_001`, `stu_001`, and so on) are public and predictable.
- **Evidence:** 8a, a rubric was created with no credentials of any kind and bound to `proj_101`. 8b, a faculty review was accepted and stored by naming `fac_001` in the body (HTTP 201, `overall_score` 76.67). 8h, a rubric created this way could not afterwards be changed or removed. 8i and 8j, peer reviews were accepted for `proj_101` under four different student ids with no credentials, and the peer block of the summary then showed four reviews with a mean of 100.
- **Impact:** anyone who can reach the service can create rubrics, submit grades as any user, and read all reviews and summaries (observed in 8c and 8d). A rubric created this way binds its projects and, because of the in-use rule, cannot be modified or deleted afterwards (8h: both a PUT and a DELETE on a bound rubric returned HTTP 409). The reports endpoint is registered the same way, with no middleware; it was not exercised by hand.
- **Why no scanner found it:** the flaw is the absence of a control. There is no code pattern for a rule to match.
- **Remediation:** require authentication with signed tokens and take the caller's identity and role from verified token claims, never from the request body.

### V2. No ownership check on review update and delete

| | |
|---|---|
| **CWE** | CWE-639 Authorization Bypass Through User-Controlled Key (related: CWE-285, CWE-862) |
| **OWASP (course list)** | A01 Broken Access Control |
| **CVSS v3.1** | `CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:H/A:N` = **7.5 High** as deployed; `PR:L` = **6.5 Medium** if V1 were fixed (the residual flaw) |
| **Layers** | route handler, data store, audit trail |

- **Root cause:** object-level authorization is missing. The route handler's `requireReview` matches a review by project id and review id only. The store runs `WHERE id = $1 AND project_id = $2`, with no reviewer condition. The `reviews` table stores `reviewer_id` but nothing compares it to the caller, and no record of who made a change is kept (`updated_at` only). Review ids are obtainable from the open list endpoint.
- **Evidence:** 8c, a PUT with no identity returned 200 and lowered a faculty grade from 76.67 to 6.67, and the summary then reported a mean of 6.67 with the grade distribution at `F: 1`. 8e, a DELETE with no identity returned 204, the review then returned 404, and the faculty review count in the summary fell to 0.
- **Impact:** silent rewriting or destruction of any grade, with no trace of the actor.
- **Why no scanner found it:** an authorization rule that was never written leaves no code to flag.
- **Remediation:** verify that the caller owns the review (or holds a role allowed to override it) before update or delete, and record the acting user.

### V3. Peer anonymity broken through error responses

| | |
|---|---|
| **CWE** | CWE-204 Observable Response Discrepancy (related: CWE-203, CWE-200) |
| **OWASP (course list)** | A01 Broken Access Control; A04 Insecure Design |
| **CVSS v3.1** | `CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:N/A:N` = **5.3 Medium** |
| **Layers** | route validation order, database constraint, identity data |

- **Root cause:** the API hides `reviewer_id` in `student_peer` responses (`presentReview`), so response bodies keep the anonymity promise. The error channel does not: the route checks user existence, role, and project membership with a different message for each, and the database unique constraint on `(project_id, reviewer_id)` surfaces as a 409 "already submitted". Each message is an oracle.
- **Evidence (8d):** HTTP 409 "This reviewer has already submitted a review for this project" confirmed that `stu_003` reviewed `proj_101`. HTTP 422 "A student_peer cannot review a project they are a member of" confirmed that `stu_001` is a member. HTTP 422 "Unknown reviewer_id: stu_999" versus "reviewer_role ... does not match the reviewer's role" lets a caller tell which ids exist and what role each has.
- **Cost to the attacker:** the 422 probes create nothing. The 409 probe needs a request that passes every earlier check, so it creates a review when the target has not yet reviewed.
- **Related effect (with V1):** the first request in 8d filed a review as `stu_003`, so the real `stu_003` would receive a 409 on their one allowed review for that project.
- **Why no scanner found it:** each response is individually correct code; the leak is in how the responses differ.
- **Remediation:** return uniform error responses for these cases and derive the reviewer from the token so claims cannot be probed.

### V4. Unbounded rubric weights: silent wrong grades, server errors, and reviewer identity in logs

| | |
|---|---|
| **CWE** | CWE-1284 Improper Validation of Specified Quantity in Input (related: CWE-190, CWE-532) |
| **OWASP (course list)** | A04 Insecure Design; A09 Security Logging and Monitoring Failures |
| **CVSS v3.1** | `CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:L/A:N` = **5.3 Medium** (the log exposure is a secondary effect and is not scored) |
| **Layers** | input validation, scoring arithmetic, database constraint, error logging |

- **Root cause:** `validation.ts` accepts any finite weight above zero, so a weight of `1e308` is valid. `computeOverallScore` sums the weights and overflows to `Infinity`. In the first case the result becomes 0; in the second it becomes `NaN`. Only the database `CHECK` on `overall_score` stops the `NaN`. The error handler then writes the full driver error, including the failing row and its `reviewer_id`, to the application log.
- **Evidence (8f):** with two criteria of weight `1e308`, 5 points on each returned HTTP 201 with `overall_score: 0`, although the correct score is 50, an unflagged wrong grade. 10 points on each returned HTTP 500, and the log showed `reviews_overall_score_check` rejecting `NaN`. **8g:** the same request as `stu_004`, a student peer, returned 500 and the log line contained `stu_004, student_peer`, so an anonymous reviewer's identity was written to the log even though the API hides it.
- **Why the tests missed it:** the agent's tests use the in-memory store, which has no `CHECK` constraint, so this path was never exercised against PostgreSQL. `pgStore.ts` has 0 of 66 lines covered (section 3.2).
- **Why no scanner found it:** this is a data-dependent arithmetic and validation bound, not a code pattern.
- **Remediation:** bound numeric ranges (maximum weight and sum), reject results that are not finite before persisting, and stop logging row data or reviewer identity in error output.

## 5. What the scanners missed, and why

Every validated vulnerability here is either the absence of a control (V1, V2), a difference between correct responses (V3), or an interaction between validation, arithmetic, the database and the logger (V4). SAST rules match code patterns, so they report nothing in code that is syntactically clean. Three facts reinforce this:

- The code is not careless in the ways the rulesets look for: queries are parameterized, the body size is limited and ids are validated.
- The one data-dependent path that reached the database (V4) lives in a file the tests never ran (0% coverage), and the scanners are blind to behavior at runtime.
- Test files were not scanned by Semgrep in this run.
